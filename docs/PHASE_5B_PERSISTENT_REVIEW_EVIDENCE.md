# Phase 5B — persistent GitHub review intelligence

New migration 20261112200647_github_review_evidence.sql was scaffolded by Supabase CLI 2.79.0 in disposable GitHub Actions. It has not been applied to hosted data. Existing evidence and governance tables are reused. A private RLS-enabled delivery receipt table and service-only RPCs validate non-demo workspace/task/reviewer, deduplicate GUIDs, serialize per workspace, reject changed tracked-branch context, ignore older observations and preserve evidence history. Identical observations refresh the current row; a state change inserts a new row and deactivates the previous row so approval cannot rely on superseded evidence.

Webhook subscriptions: Workflow run, Pull request, Pull request review. Pull requests use read-only GitHub App access; timeline permission is satisfied by Pull requests read. Signed lifecycle events trigger a fresh repository-scoped API reconciliation, not direct event-payload state writes. The two PR reads bracket the timeline query; changing state fails closed for retry. Explicit TEAMFLOW_GITHUB_REVIEW_MAPPINGS is one PR / one task / one reviewer per workspace, using immutable numeric GitHub reviewer ID and TeamFlow member UUID. Multiple reviewers on one PR, team review requests, long timeline pagination and automatic scheduled polling are deferred. A missing/truncated/ambiguous history is an inactive unknown observation, not a successful review. Duplicate delivery IDs cannot create evidence. GitHub delivery retry/redelivery is required on 503; no background queue. Review mapping changes/removal require explicit cleanup of old evidence; a changed mapping on a different PR must not be left configured without review.

Persisted review evidence feeds the existing risk engine, TIC feature extraction and recovery option API. Recovery excludes the actual GitHub reviewer, uses dated voluntary capacity for alternatives, and explicitly changes TeamFlow only. It never modifies GitHub review requests. Human approval and database version/evidence checks remain authoritative. No OpenAI spend, no provider call from a webhook, no task or plan writes from ingestion. Live GitHub App and credentials, signed GitHub delivery, actual Supabase hosted migration (only after approval), live Gemini and multi-user acceptance remain separate release gates.

Official references: https://docs.github.com/en/rest/issues/timeline and https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request_review

## Isolated acceptance workflow
Phase 5B local acceptance starts a disposable Supabase stack, creates fictional local Auth accounts, and runs the real Next.js HTTP API and desktop/mobile Chromium. A test-only Node preload intercepts GitHub API requests with a changing PR fixture. Signed request/submission/re-request events exercise real PostgREST persistence, risk/UI/TIC integration, member denial, stale approval rejection, manager approval and audit. This is not a real GitHub App installation or live provider delivery. The local stack is stopped without backup. No hosted Supabase keys are used.
